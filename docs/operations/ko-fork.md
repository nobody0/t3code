# Managed fork operations

Release preparation, deployment, recovery and the KO session helper are maintained in [nobody0/t3-code-ops](https://github.com/nobody0/t3-code-ops). Follow that repository's runbook for agent-approved updates.

This fork retains the service/update ownership guards. Upstream authentication is unchanged. The external packager preserves the installed `dist/ko-session.mjs` entrypoint for compatibility; new agents use the deployment's `tools/scripts/ko-session.mjs`.

Never run upstream update/service replacement commands against a managed fleet installation. Preserve the existing T3 home and identities. Binary rollback cannot undo database migrations.

The wrapper sets an absolute `T3_KO_MAINTENANCE_DIR`. The app publishes admission directories before rechecking the persistent `fence`; the external updater creates that fence, waits for admission directories to drain, then performs its final idle check and stop. An admitted operation cannot escape that acknowledgement. The barrier does not interrupt accepted turns, terminal subprocesses, settling events or read-only access. Without the environment variable, normal upstream behavior is unchanged.

The fence has an operations-owned identity and does not expire across crashes or app restarts. Stale permits and interrupted activation require the operations recovery procedure; the app never guesses that a lease is safe to steal. Runtime manifests advertise protocol 1 only for builds containing this implementation. The first upgrade from older builds needs a reviewed legacy drain window; subsequent updates require the running app's acknowledgement.

Carry each customization forward with its focused tests, review upstream overlap, build an immutable candidate once, and promote its exact source commit only after every intended fleet target passes. Authentication scopes, session lifetime and client pairing policy remain upstream-owned.
